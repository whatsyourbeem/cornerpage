# 프로스펙트 발굴 스크립트 (boutique-fitness)

코너페이지의 잠재고객(프로스펙트)을 자동으로 찾아서, 데모 페이지를 만들 가치가 있는 업체인지
판단하고, 그 업체의 정보를 코너페이지 입력 폼 항목에 맞춰 정리해주는 일회성 영업(GTM) 도구입니다.
**제품 코드가 아닙니다** — `src/`, `spec/`, `supabase/`는 참고용으로만 읽고 절대 수정하지 않습니다.

이 문서 하나만 읽고도 처음부터 이 작업을 이어갈 수 있도록 배경·사용법·구현 디테일을 전부 담았습니다.

---

## 1. 배경 — 왜 이 스크립트가 필요한가

**코너페이지(Cornerpage)** 는 소상공인이 업체 정보를 입력하면 미니 홈페이지가 자동 생성되는
서비스입니다(Next.js + Vercel + Supabase, 콘텐츠 생성은 Claude API, 스키마 검증은 ajv).
현재 `general`(범용)과 `boutique-fitness`(PT·필라테스·요가 스튜디오) 두 vertical을 운영하며,
`boutique-fitness`가 1차 전문화 업종입니다. 이 스크립트는 `boutique-fitness`만 다룹니다.

서비스 초기라 유입 채널이 없어서 아웃바운드 전략을 씁니다:

1. **업체 발굴** — 부티크 피트니스 업체를 찾는다 ← 이 스크립트가 담당
2. **자격 심사** — 코너페이지로 좋은 홈페이지를 만들어줄 수 있는 업체인지 판단한다 ← 이 스크립트가 담당
3. **데모 페이지 제작** — 사람이 직접 정보를 입력해 실제 페이지를 만든다 (사람이 수작업)
4. **아웃리치** — 업체에 연락해 "귀 업체 홈페이지를 만들어봤습니다"라며 링크를 보여준다 (사람이 수작업)

**중요한 원칙**: 크롤링해서 얻은 텍스트를 그대로 제품에 넣거나 재배포하지 않습니다. 오직
"이 업체가 적합한 프로스펙트인가 + 입력 폼에 뭘 채울 수 있는가"를 판단하는 내부 자료로만 쓰고,
실제 사이트 빌드 시에는 사람이 직접 정보를 입력합니다. 크롤링 원문 텍스트는 파일로 저장하지
않습니다 — Claude 판단에 쓰고 그 자리에서 버립니다. `output/`에 남는 건 요약·판단 결과뿐입니다.

## 2. 사전 준비

### 2-1. 환경변수 (`.env.local`, 저장소 루트)

```
ANTHROPIC_API_KEY=...              # 이미 제품 코드가 쓰는 것과 동일 (없으면 팀에 요청)
NAVER_APIGW_API_KEY_ID=...         # NAVER API HUB 지역검색 키 ID
NAVER_APIGW_API_KEY=...            # NAVER API HUB 지역검색 키
```

`.env.local`은 `.gitignore`에 이미 포함돼 있습니다(`.env*` 패턴). **네이버 키를 여기 README나
코드에 하드코딩하지 마세요** — 키가 없으면 팀(제이현)에게 요청하세요.

⚠️ 네이버 지역검색은 **레거시 방식(`openapi.naver.com` + `X-Naver-Client-Id` 헤더)이 아니라
2026-06-25 출시된 NAVER API HUB**를 씁니다. 레거시 문서가 검색 결과에 훨씬 많이 나오지만
그 방식으로는 이 키가 인증 실패(에러코드 024)합니다. 실제로 동작하는 엔드포인트는 3-1절 참고.

### 2-2. 의존성

프로젝트에 이미 있는 `@anthropic-ai/sdk`, `tsx`만 씁니다. 별도 설치 불필요.
`dotenv`는 일부러 안 씀 — 이 스크립트가 직접 `.env.local`을 파싱합니다(코드 상단 `loadEnvLocal()`).

## 3. 사용법

```bash
npx tsx scripts/prospect-discovery/discover.ts "매탄동 필라테스"
```

- 인자는 **검색 쿼리 하나**(지역+키워드 조합), 사람이 직접 지정합니다. **스크립트가 지역×키워드를
  자동으로 조합하게 만들지 마세요** — 원 지시사항의 명시적 요구사항입니다.
- 실행 시간은 대상 블로그 글 수에 비례합니다(크롤링 딜레이 1.5초/글 + Claude 호출 시간). 블로그
  1곳당 보통 수십 초~2분 정도.
- 결과는 콘솔에도 출력되고, `scripts/prospect-discovery/output/{쿼리}-{타임스탬프}.md`에도
  저장됩니다. 이 폴더는 git에 커밋해도 됩니다(원문이 아니라 요약만 담기므로) — 다만 커밋은
  사용자가 명시적으로 요청할 때만 하세요.
- 디버그: `DEBUG_EXTRACTION=1` 환경변수를 붙이면 Claude가 추출한 원본 JSON을 콘솔에 그대로
  출력합니다.

## 4. 동작 흐름

```
[1] 사람이 검색 쿼리 지정 (예: "매탄동 필라테스")
      ↓
[2] 네이버 지역검색 API 호출(sort=random + sort=comment 2회) → 업체 최대 10개 획득 → 상호명+좌표로 dedup
      ↓
[3] link 필드가 blog.naver.com인 업체만 필터링 (인스타/유튜브/자체사이트 등은 제외)
      ↓
[4] 블로그 글 목록 조회 (최근 것부터 최대 100개)
      ↓
[5] 글이 5개 미만 → "부적합"으로 보고 본문 크롤링 생략 (비용 절약)
    글이 5개 이상 → "적합"으로 보고 목록에 있는 글 전부(최대 100개) 본문 크롤링
      ↓
[6] Claude가 크롤링한 전체 텍스트를 읽고 input-questions.md 항목별 답을 JSON으로 추출
      ↓
[7] 수집한 이미지 URL을 Claude Vision에 보내 로고/공간사진/트레이너사진/기타로 분류
      ↓
[8] 마크다운 리포트로 조립해 콘솔 출력 + output/ 저장
```

### 왜 블로그 링크만 고르는가

- **인스타그램을 대표 링크로 걸어둔 업체는 제외**합니다. 이미 인스타를 잘 운영 중이라 별도
  홈페이지 필요성이 낮습니다.
- **블로그를 걸어둔 업체가 타겟**입니다. 코너페이지가 대체할 수 있는 대상이면서, 동시에 텍스트
  정보가 풍부해 심사에 필요한 재료가 많습니다.

### "적합" 판정 기준 — 글 5개 이상

`MIN_POSTS_FOR_ELIGIBLE = 5` ([discover.ts](discover.ts)). **이건 읽는 글 개수의 상한이 아니라
최소 기준선입니다.** 글이 5개 미만이면 판단 재료 자체가 부족하다고 보고 크롤링을 생략합니다.
5개 이상이면 그 블로그에 있는 글을 **전부**(단, 목록 조회 자체를 최근 100개로 제한하므로 최대
100개까지) 읽습니다. 실제로 글이 딱 5개인 작은 블로그를 심사하면 "5/5개 읽음"으로 나올 수
있는데, 이건 5개만 읽고 멈춘 게 아니라 그 블로그에 진짜 5개밖에 없기 때문입니다.

이 기준은 이전 버전(6개 필수 항목이 전부 있어야 통과하는 게이트 방식)에서 사용자 지시로
단순화된 것입니다 — "글이 5개 정도 있으면 거기서 충분히 필요한 정보를 추출할 수 있을 것"이라는
가정입니다. 필수 항목이 비어 있어도 부적합 처리하지 않고, 대신 부족한 항목은 리포트의
"못 채운 항목"에 기록해서 사람이 나중에 직접 물어보게 합니다.

100이라는 목록 조회 상한(`POST_LIST_FETCH_COUNT`, 60에서 100으로 상향— 더 꼼꼼히 살펴봐야
한다는 사용자 지시)은 여전히 임의로 정한 값입니다 — 이 값을 훨씬 넘는(수백 개 이상) 초대형
블로그에서 `PostTitleListAsync.naver`가 실제로 상한 없이 다 돌려주는지는 검증 못 했습니다
(테스트한 실제 부티크 피트니스 블로그들은 전부 글이 5개뿐이라 큰 값을 넣어도 항상 실제
개수만 돌아옴 — `countPerPage=200`으로 실측해도 에러 없이 정상 동작하는 것만 확인). 글이 아주 많은
블로그를 더 깊이 읽고 싶으면 이 상수를 올리면 됩니다(크롤링 시간이 그만큼 늘어남).

## 5. 출력 형식

리포트는 4개 섹션으로 구성됩니다:

1. **적합 — 입력 폼 초안**: 업체별로 `spec/for-frontend/boutique-fitness/input-questions.md`의
   STEP 2~6 항목을 채운 결과. 정보가 없는 항목은 "❌ 정보없음"으로 표시하고, 리포트 하단
   "못 채운 항목"에 다시 한번 정리해서 사람이 데모 제작 전 뭘 직접 물어봐야 하는지 한눈에
   보이게 합니다. STEP 2 다음에 **"이미지 후보"** 섹션이 따로 있는데, 크롤링한 블로그 글의
   이미지 전부를 Claude Vision이 실제로 보고 로고/공간사진/트레이너사진/기타로 분류한
   결과입니다(6-3절 참고) — 이미지 자체는 다운로드하지 않고 원본 URL만 나열하므로, 데모
   페이지 제작 시 사람이 URL을 열어서 직접 다운로드해야 합니다.
2. **부적합 (글 5개 미만)**: 업체명·주소·블로그 URL·실제 글 개수만 간단히 기록.
3. **처리 실패**: 크롤링/API 오류로 판단 자체를 못 한 업체와 실패 사유.
4. **제외됨 (블로그 링크 아님)**: 대표 링크가 인스타/유튜브/자체사이트 등이라 애초에 대상에서
   빠진 업체.

### STEP 2~6 항목이 뭔지 궁금하면

원본은 `spec/for-frontend/boutique-fitness/input-questions.md`입니다(제품 코드, 읽기 전용).
`discover.ts`의 `EXTRACTION_SYSTEM_PROMPT`가 이 문서를 심사·추출용으로 압축한 버전을 담고
있습니다. **원본이 업데이트되면 프롬프트도 그에 맞춰 갱신해야 합니다** — 지금은 수동 동기화라
드리프트 가능성이 있습니다.

## 6. 구현 디테일 / 알려진 함정 (실측으로 확인된 것들)

새 세션에서 같은 삽질을 반복하지 않도록 실제로 부딪혔던 문제와 해결책을 기록합니다.

### 6-1. 네이버 지역검색 (NAVER API HUB)

```
GET https://naverapihub.apigw.ntruss.com/search/v1/local
Headers:
  X-NCP-APIGW-API-KEY-ID: {NAVER_APIGW_API_KEY_ID}
  X-NCP-APIGW-API-KEY: {NAVER_APIGW_API_KEY}
Params:
  query   — 검색어 (UTF-8)
  display — 최대 5 (네이버가 트래픽 문제로 제한, 그 이상 요청해도 5로 잘림)
  sort    — random | comment
```

- `title`에 검색어가 `<b>` 태그로 감싸져 옴 → 제거 필요 (`extractBlogId` 전에 처리됨)
- `telephone`은 항상 빈 문자열로 옴 — 전화번호로 dedup 불가, **상호명+좌표 조합**으로 dedup
- `mapx`/`mapy`는 10,000,000으로 나누면 경도/위도
- `link`는 네이버플레이스가 아니라 **사업자가 대표로 설정한 외부 링크**(블로그/인스타/유튜브 등)
- 같은 건물에 층만 다른 업체가 여러 개 있을 수 있어서 **좌표 완전일치만으로 중복 처리하면 안 됨**
  (상호명까지 같아야 진짜 중복) → `dedupByNameAndCoords()`가 이미 이렇게 처리함

**`display` 5 상한을 넘기는 법 — `start`는 안 먹힘, `sort` 두 번 호출로 우회**: 공식 페이지네이션
파라미터로 보이는 `start`(정수)를 실측해봤는데 **완전히 무시됩니다** — `start=1`/`start=6`/`start=100`
모두 응답이 100% 동일하고, 응답의 `"start"` 필드도 요청값과 무관하게 항상 `1`로 고정되어 옵니다.
`"total"` 필드도 실제 매칭 총개수가 아니라 그냥 `display` 값을 그대로 되돌려주는 것으로 보입니다
(전국 대상 "필라테스" 단독 검색도 `total: 5`로 나옴 — 실제로는 훨씬 많을 수밖에 없는 쿼리인데도).

대신 `sort=random`과 `sort=comment`는 **실제로 서로 다른 5개**(일부만 겹침)를 줍니다(`sort` 생략 시
기본값은 `random`과 동일). `searchNaverLocalCombined()`가 두 sort를 병렬 호출해서 합친 뒤
`dedupByNameAndCoords()`로 중복만 제거합니다 — 한 쿼리당 최대 10개(보통 겹치는 게 있어 8~9개
정도)까지 늘어납니다. 그 이상(예: 15개, 20개)을 원하면 이 두 값 외의 다른 `sort` 값이 있는지
더 찾아보거나, 쿼리 자체를 세분화해서 여러 번 실행하는 수밖에 없습니다(2절 원칙대로 쿼리
조합은 사람이 직접 정함).

### 6-2. 블로그 글 목록 조회

`m.blog.naver.com` 모바일 홈은 글 목록이 클라이언트 사이드에서 로드돼서 정적 HTML에 안 잡힘.
대신 레거시 PC 비동기 API가 SSR 없이 바로 JSON을 줌:

```
GET https://blog.naver.com/PostTitleListAsync.naver
    ?blogId={blogId}&viewdate=&currentPage={page}&categoryNo=&parentCategoryNo=&countPerPage={N}
```

**함정 1**: 이 응답의 `pagingHtml` 필드가 작은따옴표를 `\'`로 이스케이프해서 내려오는데, 이건
유효한 JSON escape가 아닙니다(JSON은 `\"`만 허용, `\'`는 안 됨). `res.json()`이나 그냥
`JSON.parse`를 쓰면 `Bad escaped character in JSON` 에러로 100% 실패합니다.
`fetchPostListPage()`가 `.replace(/\\'/g, "'")`로 먼저 치환한 뒤 파싱합니다.

**함정 2 (훨씬 치명적이었음)**: `countPerPage`를 아무리 크게 보내도(100, 200 등) **서버가
조용히 5로 고정**합니다 — 응답의 `parameters.countPerPage`를 까보면 항상 `"5"`로 찍혀 있고,
`postList`도 정확히 5개만 옵니다. 에러도 안 나고 `resultCode: "S"`(성공)로 응답하기 때문에
겉보기엔 요청이 잘 처리된 것처럼 보입니다. **이것 때문에 실제로 사고가 났습니다**: 처음엔
"이 블로그들은 진짜 글이 5개뿐이구나"라고 잘못 결론 내렸는데, 사용자가 "그 블로그 글 149개인데?"
라고 지적해서 뒤늦게 발견했습니다 — `totalCount` 필드(응답에 존재하며 실제 총 글 수를 정확히
줌, 실측으로 149/247/24 등 확인)를 안 보고 `postList.length`만 신뢰한 게 원인이었습니다.

**교훈**: 이런 종류의 스크래핑 대상 API에서 개수 관련 파라미터는 **요청값과 응답의 `parameters`
echo 필드가 실제로 일치하는지, 그리고 별도 total 필드가 있다면 그것과 대조해서** 확인해야
합니다 — `resultCode: "S"`만 보고 "정상 응답이니 요청대로 처리됐겠지"라고 넘겨짚으면 안 됩니다.

**해결**: `countPerPage`로 한 번에 많이 받는 걸 포기하고, `currentPage`로 페이지네이션합니다
— 이건 정상 동작합니다(각 페이지가 서로 다른 5개를 정확히 줌, 실측 확인). `fetchRecentPostList()`가
`currentPage=1,2,3...`을 돌며 `POST_LIST_FETCH_COUNT`개(현재 100)를 모을 때까지, 또는
`totalCount`에 도달할 때까지 반복합니다. 적합/부적합 판정(총 글 5개 이상인지)은 **첫 페이지의
`totalCount`만으로 즉시 결정**하고(`main()`의 `firstPage` 처리), 부적합이면 나머지 페이지를
안 가져와서 낭비를 줄입니다.

RSS(`https://rss.blog.naver.com/{blogId}.xml`)도 동작하지만 본문이 잘린 요약만 주기 때문에
목록 조회 용도로는 안 씁니다.

### 6-3. 블로그 본문 크롤링

```
GET https://m.blog.naver.com/{blogId}/{logNo}
```

본문은 `<div class="se-main-container">` (네이버 스마트에디터 wrapper) 안에 있습니다.
정규식으로 자르면 중첩된 `</div>`에서 깨지므로, `extractMainContainer()`가 **태그 개수를
세어가며 균형 매칭**으로 정확히 잘라냅니다.

User-Agent를 모바일로 위장해야 합니다(`UA` 상수) — 데스크톱 UA로는 리다이렉트/다른 레이아웃이
나올 수 있습니다. 요청 간 1.5초 딜레이(`CRAWL_DELAY_MS`)를 반드시 유지하세요 — 연속 요청 시
차단될 수 있습니다.

### 6-3-1. 이미지 URL 추출 + Claude Vision 분류

본문 안의 `<img>` 태그에서 진짜 이미지 URL을 뽑는 게 생각보다 까다롭습니다:

- **함정**: `src` 속성은 지연로딩용 블러 플레이스홀더(`?type=w80_blur`)라 항상 흐릿한
  썸네일입니다. **진짜 이미지는 `data-lazy-src` 속성에 있습니다**(실측 확인, `?type=w400`
  또는 `w800` 사이즈). `extractImages()`가 `data-lazy-src`를 우선 쓰고 없으면 `src`로
  폴백합니다.
- **함정**: `class="se-sticker-image"`가 붙은 `<img>`는 네이버 블로그 이모티콘 스티커입니다
  (`storep-phinf.pstatic.net` 호스팅) — 실제 사진이 아니므로 제외해야 합니다.

수집한 이미지 URL(업체당 최대 `MAX_IMAGES_FOR_VISION`개, 현재 24)을 Claude Vision에 보내
로고/공간사진(space)/트레이너사진(trainer)/기타(other)/제외(exclude) 5개 카테고리로
분류시킵니다(`classifyImages()`). input-questions.md STEP 2(로고·공간사진·기타사진)와
STEP 4(트레이너 개인사진)가 요구하는 카테고리와 맞춰져 있습니다.

**함정**: Claude API의 URL 소스 이미지 블록(`source.type: "url"`)에 pstatic.net URL을 그대로
넘기면 **"Unable to download the file. Please verify the URL and try again."로 100% 실패**합니다
(실측 확인 — 같은 URL을 우리 쪽에서 `curl`로 요청하면 헤더 없이도 200이 오는 걸 보면 Anthropic
서버 쪽 다운로더가 이 호스트를 못 받아오는 것으로 보입니다. Referer/UA 문제는 아닌 것으로
확인됨). 그래서 이미지를 **우리가 직접 다운로드해서 base64로 인코딩**해 보냅니다
(`fetchImageAsBase64()`, `source.type: "base64"`). 이미지 자체는 메모리에서만 다루고 디스크에
저장하지 않습니다.

이미지는 다운로드 자체는 하지만(vision 분류를 위해 base64로 변환) **원본을 파일로 저장하지도,
리포트에 임베드하지도 않습니다** — 리포트에는 분류 결과와 함께 원본 URL만 남습니다. 데모 페이지
제작 시 사람이 그 URL을 열어서 다운로드하면 됩니다.

### 6-4. Claude 추출이 가끔 깨진 JSON을 줌

두 가지 실패 패턴이 실측됨:

1. `max_tokens`가 부족해서 JSON이 문장 중간에 잘림 (코드펜스 닫는 ` ``` `도 못 나옴)
2. 모델이 가끔 오타성 문자를 섞음 (예: `"...충족한다.";,` 처럼 세미콜론이 섞여 들어감)

대응: `max_tokens: 8192`로 충분히 크게 잡고, `src/lib/generate-content.ts`의 repair loop과
동일한 패턴으로 파싱 실패 시 오류 메시지를 모델에게 보여주고 최대 2회 재요청합니다
(`extractDraftAnswers()`의 `MAX_JSON_REPAIR_ATTEMPTS`). 코드펜스가 안 닫힌 채로 잘린 경우도
처리하도록 정규식은 `` /```(?:json)?\s*([\s\S]*?)(?:```|$)/ ``로 닫는 펜스를 옵션 처리함.

### 6-5. 등급 산정을 왜 Claude한테 안 맡기나

이전 버전은 A/B/C/부적합 등급까지 Claude가 매기게 했었는데, 지금은 **적합/부적합 이분법이고
그마저도 실제 글 개수(코드에서 결정적으로 계산)로 판정**합니다. Claude는 사실 추출만 담당—
"이 값이 있다/없다/뭐다"만 뽑고, 판정 자체는 코드가 함으로써 실행할 때마다 판정이 흔들리는
문제를 없앴습니다.

  전용으로 하드코딩돼 있습니다. 다른 업종을 다루려면 `spec/for-frontend/general/input-questions.md`

  싶으면 올리세요 — 크롤링 시간이 비례해서 늘어납니다.

  일부만 분류됩니다(최근 글부터 순서대로 담은 목록의 앞부분만 사용) — 올리면 Vision 호출
  비용·시간이 늘어납니다.
