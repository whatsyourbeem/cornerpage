## 확정된 블록 순서 (Step 2 최종)

```
0. 상단 고정바
1. 히어로
2. 신뢰 스트립
3. 비포/애프터 (transformations)         ← 신규
3-1. 리뷰 (reviews)
3-2. 전문가 프로필 (professionals)        ← 신규
3-3. 철학 (philosophy)
4. 분위기(atmosphere) + 갤러리 + 시설 스펙(facility) ← facility 신규
5. 메뉴/서비스 (item_consult)
6. 위치/정보
7. 하단 고정 CTA바
8. 이용방법
9. FAQ
```

**`lead_emphasis`(사장님이 직접 고르는 최우선 어필 포인트: transformations/reviews/professionals/facility)에 따라 3~3-2 구간의 순서가 바뀐다.** facility가 선택된 경우에만 예외적으로 공간 클러스터(4번)에서 분리되어 최상단으로 이동한다. 상세 로직은 아직 미정 — 이 블록들 각각을 정의할 때 함께 확정한다.

**"나도 할 수 있을까"(초보자 배려) 불안은 별도 블록 없이 `professionals`의 필드 + FAQ 필수 문항으로 분산 처리한다.**

## 블록 0. 상단 고정바

### 층1 (슬롯 구조)
general과 동일. 신규 필드 없음.
```json
"topbar": {
  "display_name": "string, required",
  "action_button": { "type": "call | reservation | direction", "label": "string" }
}
```

### 층2 (작성 원칙)
- general 원칙(로고/가게명 배치, 메뉴 햄버거 넣지 않음 — 이탈 링크이자 집중 원칙 위반) 그대로 유지.
- **내비게이션 메뉴(섹션 앵커 이동)는 검토 후 최종적으로 넣지 않기로 결정.** 이유: (1) 스키마·질문지·evals 전반에 관리 표면적이 늘어나는데 비해 실익(스크롤 절감 정도)이 작음, (2) 이 vertical의 핵심 설계 철학인 "방문자가 증거를 정해진 순서로 지나가게 하는 선형적 설득 경로"와 충돌 — 네비게이션은 본질적으로 자유 점프를 허용하는 브라우징형 UX라 철학에 틈을 만듦.
- **`action_button.type` 기본값 = `reservation`.** general의 토르짐(헬스장) 예시에서 이미 "PT 상담 예약"을 `reservation` 타입 + 커스텀 라벨로 처리한 선례가 있음 — 새 타입을 만들 필요 없이, `type`은 기술적 동작만 담당하고 "상담"이라는 뉘앙스는 `label`이 담당.
- **`cta_interaction_mode` 기본값 = `guided`.** Step1의 "강매 불안" 특성상 대부분 실제 상담 창구는 카톡·DM 등 사람 응대. `functional`은 예외적인 경우만.
- **라벨은 항상 저부담 문구로 고정.** "무료상담 신청", "체험 문의하기" 등만 허용. **"지금 등록", "결제하기", "구매하기" 같은 즉시결제성 라벨은 금지** — 상단바에서부터 강매 인상을 주면 안 됨.

### 층2.5 (좋은/나쁜 예)
**좋은 예:** `{ "type": "reservation", "label": "무료상담 신청" }`
**나쁜 예:** `{ "type": "reservation", "label": "지금 바로 등록하기" }` — 상담도 안 받았는데 등록을 압박.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 10-1절)

## 블록 1. 히어로

### 층1 (슬롯 구조)
general과 동일, 신규 필드 없음.
```json
"hero": {
  "badge": "string, required",
  "headline": "string, required",
  "tagline": "string, required",
  "background_image_url": "url | null",
  "cta": { "type": "call | reservation | direction", "label": "string" }
}
```

### 층2 (작성 원칙)
general 원칙(3초 안에 읽힘, 감정 형용사 금지, 구체적 장면) 그대로 유지하되, 이 vertical 특화 사항:

- **배지**: 지역 + **구체적 전문 분야**로. "헬스장" 같은 뭉뚱그린 표현 대신 "PT 전문 스튜디오", "필라테스 스튜디오", "요가 지도자 스튜디오"처럼 구체화 — `definition.md`의 "웜 트래픽" 특성상 방문자는 이미 어느 정도 관심이 있는 상태라, 모호한 업종명보다 구체적 전문성이 3초 안의 인지에 더 유리함.
- **헤드라인 — 이 vertical만의 추가 제약**: **아직 증거(비포애프터·리뷰)를 보여주기 전 단계이므로, 결과를 과장 약속하는 문구는 금지.** "확실한 변화를 만들어드립니다" 같은 문구는 최상급 표현 회피 원칙에도 걸리고, 뒤에 나올 증거 블록의 역할을 헤드라인이 미리 가로채는 셈이라 구조상으로도 어색함. 헤드라인은 **정체성·전문성의 구체적 사실**에 뿌리박는다(경력 연차, 전문 분야, 지도 방식 등) — "결과 약속"이 아니라 "이 사람/공간이 어떤 존재인지"까지만.
- **태그라인 — 이 vertical만의 역할 지정**: general은 "헤드라인이 못 담은 핵심 사실 보강"이라는 중립적 역할만 주지만, 이 vertical은 여기에 **`definition.md` 5장의 "나도 할 수 있는 수준일까?"라는 미해결 불안을 배치한다.** 아직 어느 블록도 이 불안을 명시적으로 안 맡고 있었는데, 방문자가 스크롤하기도 전에(헤드라인 바로 아래) 가장 먼저 마주치는 자리라 여기가 최적이다. 단, 과장 없이 사실 기반으로: "운동이 처음이어도 괜찮습니다" 같은 일반론이 아니라 사장님이 준 사실(예: "초보 회원 비중 70%")이 있으면 그걸 쓰고, 없으면 절제된 일반 문구로 대체.
- **CTA**: 상단고정바와 동일 원칙 — `reservation` 타입, 저부담 라벨.

### 층2.5 (좋은/나쁜 예)
**좋은 예 (헤드라인):** "8년째 재활 전문으로, 한 사람만 보는 PT" — 사실(경력·전문분야·1:1 방식) 기반, 결과 약속 없음.
**나쁜 예:** "당신의 몸을 확실히 바꿔드립니다" — 증거 없이 결과부터 약속(최상급·과장 위험), 뒤에 나올 `transformations`·`reviews` 블록이 담당해야 할 역할을 가로챔.
**좋은 예 (태그라인):** "운동 경험이 없는 회원님이 전체의 70%입니다" — 초보자 불안을 사실로 해소.
**나쁜 예 (태그라인):** "누구나 편하게 즐기는 곳" — 사실 근거 없는 일반론, AI 티 위험.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 10-2절)

## 블록 2. 신뢰 스트립

### 층1 (슬롯 구조)
general과 동일:
```json
"trust_strip": {
  "items": [ { "value": "string", "label": "string" } ]
}
```

### 층2 (작성 원칙)
general 원칙(지표 3개, 진실성, 데이터 없으면 대체)은 유지하되, **지표의 내용을 이 vertical 특화로 한정**:

- 우선순위: (1) 트레이너 경력 연차, (2) 누적 회원 변화 수 또는 보유 자격증 수, (3) 운영 연차 또는 상담 건수 중 데이터가 있는 것.
- **일반 헬스장식 지표(평수·기구 개수·24시간 운영 등)는 신뢰 스트립에 넣지 않는다** — 이 정보는 `facility` 블록의 몫. 신뢰 스트립은 "사람과 성과"에 집중, 시설 정보와 섞이면 `definition.md`의 "신뢰 근거 위계"가 흐려짐.
- 데이터가 부족하면(신생 스튜디오 등) `industry-data.md`의 대체 지표 후보를 참고(작성 예정).

### 층2.5 (좋은/나쁜 예)
**좋은 예:** "8년 · 지도 경력" / "127명 · 누적 변화 사례" / "4개 · 보유 자격증" — 사람·성과 중심.
**나쁜 예:** "500평 · 규모" / "24시간 · 운영" — 시설 지표가 신뢰 스트립에 섞임, `facility` 블록으로 이동해야 함.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 10-3절)

## 블록 3. 비포/애프터 (`transformations`, 신규)

### 층1 (슬롯 구조)
```json
"transformations": {
  "items": [
    {
      "before_image_url": "url, required",
      "after_image_url": "url, required",
      "duration_label": "string, required (예: '12주')",
      "result_highlight": "string, required (핵심 수치·변화 요약, 예: '-8kg', '체지방률 6%p 감소')",
      "member_label": "string (익명 처리, 예: '김○영님' — reviews의 author 마스킹 관례와 동일)",
      "trainer_tag": "string | null (담당 전문가 이름 — professionals 블록과 느슨하게 연결)"
    }
  ]
}
```
`items`가 비었으면 `transformations: null`. 권장 개수 1~4개(리뷰·갤러리처럼 4~8장 채우는 성격이 아니라, 사례 하나하나가 무거운 증거라 억지로 개수를 채우지 않는다).

### 층2 (작성 원칙)
- **`before_image_url`·`after_image_url`·`duration_label`·`result_highlight` 4개 모두 필수.** 사진만 있고 기간·수치가 없으면 이 블록을 켜지 않는다 — `design-guide.md`의 원칙("맥락 없는 사진은 증거력이 약함")을 스키마 레벨에서 강제하는 것.
- **이 블록은 사실 조작 리스크가 가장 큰 블록이다.** `copywriting.md`의 "없는 걸 지어내지 않는다" 원칙이 다른 어느 블록보다 엄격하게 적용돼야 한다 — 사장님이 실제로 제공한 회원 사진·데이터만 쓴다. 각도를 트는 것(카피 표현)과 결과를 과장하는 것(없는 수치를 만들어내는 것)은 다르다.
- **`member_label`은 reviews와 동일한 마스킹 관례**를 따른다(`김○영님`). 실명 노출 금지.
- **`trainer_tag`는 선택이지만 있으면 적극 채운다.** `professionals` 블록과 연결되면 "누가 이 결과를 만들었는지"가 분명해져 직접증거(성과)와 간접증거(전문가)가 서로를 보강한다 — `definition.md` 4장의 증거 위계가 실제로 작동하는 지점.
- **캡션에 과장된 수식어를 붙이지 않는다.** 수치 자체가 증거이므로, "놀라운 변화!" 같은 감탄사형 카피는 오히려 `copywriting.md`의 AI 티 방지 원칙에 걸린다.

### 층2.5 (좋은/나쁜 예)
**좋은 예:** `{ "duration_label": "12주", "result_highlight": "체지방률 6%p 감소", "member_label": "김○영님", "trainer_tag": "박현우 트레이너" }` — 기간·수치·담당자까지 명확.
**나쁜 예 1:** `{ "duration_label": null, "result_highlight": "환상적인 변화!" }` — 기간 없음, 수치 없이 감탄사만. 증거력 없음.
**나쁜 예 2:** 사장님이 안 준 수치를 그럴듯하게 지어내는 것 — 이 블록에서는 특히 절대 금지(광고 신뢰성 문제로 직결).

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 4-1절 — 좌우 드래그 슬라이더, 시그니처 인터랙션)

## 블록 3-1. 리뷰 (`reviews`)

### 층1 (슬롯 구조)
```json
"reviews": {
  "items": [
    {
      "body": "string, required (유저 입력 원문 그대로, 가공 금지)",
      "rating": "number | null",
      "author": "string (익명 처리, 예: '김○영')",
      "source": "string | null (예: '네이버 예약', '카카오맵', '인스타그램 DM')",
      "trainer_tag": "string | null (리뷰 원문에 담당 전문가 이름이 언급된 경우만 채움 — 절대 추론·생성 금지)"
    }
  ]
}
```
general 대비 `trainer_tag` 필드 추가 — `transformations`와 동일한 패턴으로, "누가 이 결과를 만들었는지"를 리뷰에서도 연결한다.

### 층2 (작성 원칙)
- **원문·익명화·null 처리는 general과 동일** — 절대 원문을 각색·요약하지 않는다.
- **`trainer_tag`는 리뷰 원문에 실제로 이름이 등장할 때만** 채운다. "아마 이 트레이너겠지" 식 추론 절대 금지 — `transformations`의 사실 조작 금지 원칙과 동일 수위로 엄격하게 적용.
- **이 블록은 `transformations` 바로 다음, 사실상 필수급으로 취급한다.** `definition.md` 4장에서 리뷰를 "제3자 목소리라 선별 편향 의심을 우회하는 독립적 증거"로 정의했다 — 데이터 없으면 null이라는 general의 소극적 태도와 달리, 이 vertical은 `industry-data.md`·`input-questions.md` 단계에서 리뷰 확보를 적극적으로 유도해야 한다(작성 예정 파일들에 반영).
- **여러 개 있으면 비슷한 내용보다 다각도로 고른다** — 효과(성과)·친절함(전문가)·시설 중 겹치지 않는 관점의 리뷰를 우선 배치해, 이미 앞 블록들(비포애프터)이 증명한 것과 다른 각도의 증거를 추가한다.

### 층2.5 (좋은/나쁜 예)
**좋은 예:** `{ "body": "박현우 트레이너님한테 3개월 배웠는데 자세 교정부터 꼼꼼히 봐주셨어요", "author": "김○영", "source": "네이버 예약", "trainer_tag": "박현우" }` — 원문에 이름이 직접 등장해서 `trainer_tag` 채움.
**나쁜 예:** 리뷰 원문엔 트레이너 이름이 없는데 "아마 대표님이겠지" 하고 `trainer_tag`를 임의로 채우는 것 — 절대 금지.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 4-2절 — `trainer_tag`는 작성자 옆에 `tag-cert` 스타일의 작은 칩으로 표시)

## 블록 3-2. 전문가 프로필 (`professionals`, 신규)

### 층1 (슬롯 구조)
```json
"professionals": {
  "section_label": "string, required (예: '트레이너 소개', '강사진 소개', '요가 지도자 소개' — 실제 업종 언어로)",
  "items": [
    {
      "name": "string, required",
      "title": "string, required (예: '대표 트레이너', '필라테스 강사', '원장')",
      "photo_url": "url | null",
      "certifications": ["string"],
      "specialty": "string, required (전문분야 한 줄)",
      "years_experience": "number | null",
      "bio_quote": "string, required (한 줄 지도철학)"
    }
  ]
}
```
`items` 최소 1개 — **이 vertical에서는 필수 블록**(general엔 대응 블록 자체가 없음, `definition.md`가 "신뢰 단위=사람"이라 명시한 근거가 여기서 스키마로 구현됨). 원장 1인 스튜디오면 1개, 팀이면 N개로 동일하게 대응.

### 층2 (작성 원칙)
- **`section_label`은 업종 세부 유형에 맞게 자유 텍스트로.** general의 "메뉴 라벨을 업종 언어로"(카페=대표 메뉴, 미용실=주요 시술) 원칙과 같은 패턴 — PT면 "트레이너 소개", 필라테스면 "강사진 소개", 요가면 "요가 지도자 소개".
- **`certifications`는 실제 보유한 것만.** `copywriting.md`의 "없는 걸 지어내지 않는다" 원칙이 그대로 적용 — 여기가 특히 위험한 이유는 자격증 사칭이 단순 과장이 아니라 신뢰·법적 문제로 직결되기 때문. 자격증이 없으면 빈 배열(`[]`)로 두고, `years_experience`·`specialty`로 신뢰를 보강한다(신뢰 스트립의 "대체 지표" 논리와 동일).
- **`bio_quote`는 과장 없이 자연스러운 문장으로.** *(design-guide.md에서 옮겨온 원칙)* 이 블록의 목적은 전문성을 전달하는 것이지 감성적으로 띄우는 게 아니다 — "대한민국 최고의 트레이너" 같은 최상급 자기소개는 `copywriting.md` 4번 원칙 위반. 가능하면 "나도 할 수 있을까"라는 불안(`definition.md` 5번, 히어로 태그라인과 이어지는 지점)을 살짝 완화하는 방향이면 더 좋다 — 단, 사장님이 준 사실에 그런 뉘앙스가 있을 때만(예: "초보자도 부담 없이" 같은 실제 지도 방침이 있을 때).
- **여러 명일 때 순서**: `meta.lead_emphasis`가 `professionals`로 선택된 경우 대표/에이스 트레이너를 맨 앞에 배치, 아니면 사장님이 제공한 순서를 그대로 따른다.

### 층2.5 (좋은/나쁜 예)
**좋은 예:** `{ "name": "박현우", "title": "대표 트레이너", "certifications": ["생활스포츠지도사 2급", "NSCA-CPT"], "specialty": "체형교정·재활 운동", "years_experience": 8, "bio_quote": "운동이 처음인 분들이 다치지 않게, 기본기부터 차근차근 봐드립니다." }`
**나쁜 예 1:** `certifications`에 실제로 없는 자격증을 채우는 것 — 절대 금지, 신뢰·법적 리스크.
**나쁜 예 2:** `"bio_quote": "대한민국 최고의 실력으로 인생을 바꿔드립니다"` — 최상급·과장, 이 블록의 목적(전문성 전달)에서 벗어남.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 4-1절)

## 블록 3-3. 철학 (`philosophy`)

### 층1 (슬롯 구조)
general과 동일, 변경 없음:
```json
"philosophy": {
  "text": "string"
} | null
```

### 층2 (작성 원칙)
- STEP3 계기·철학 답변 있을 때만, 없으면 `null` — general과 동일.
- 2~4문장, 인용구 톤 — general과 동일.
- **위치 재정의**: general은 "Manifesto는 일찍 보여줘야 임팩트가 산다"는 이유로 hero 직후 고정이지만, 이 vertical은 **의도적으로 증거 클러스터(비포애프터→리뷰→전문가) 뒤로 미룬다.** `definition.md` 4장의 결론(직접증거 우선, 간접·정성적 요소는 그다음)과 정확히 같은 논리 — 철학은 "이 사람을 믿어도 될까"에 대한 답이 아니라 "이 사람이 왜 이 일을 하는가"에 대한 답이라, 신뢰가 어느 정도 쌓인 뒤에 읽혀야 감동이 되지, 먼저 나오면 근거 없는 선언처럼 들릴 위험이 있다.
- **범위 재정의**: `professionals.bio_quote`가 이미 "개인의 지도 철학"을 담당하므로, 이 블록은 **스튜디오 차원의 계기**로 한정한다(예: "왜 이 공간을 열었는가"). 트레이너 개인 서사와 겹치면 같은 이야기가 두 블록에서 반복돼 지루해진다 — 이건 general에 없던 문제로, boutique-fitness가 `professionals`라는 새 블록을 만들면서 생긴 신규 제약이다.

### 층2.5 (좋은/나쁜 예)
**좋은 예:** "다치지 않고 오래 운동할 수 있는 공간이 없어서, 직접 만들었습니다." — 스튜디오 창립 계기, 개인 지도 스타일 얘기 아님.
**나쁜 예:** "저는 항상 회원님 한 분 한 분께 최선을 다합니다" — 이건 `professionals.bio_quote`가 담당할 개인 서사가 잘못 자리 잡은 경우.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 4-2절 — general의 Manifesto 변형(큰 타이포·인용구 강조) 재사용 가능, 위치만 다름)

## 블록 4. 공간 클러스터 (분위기 + 갤러리 + 시설 스펙)

세 블록은 "공간을 보여준다"는 공통 목적으로 인접 배치된다. `meta.lead_emphasis`가 `facility`로 선택된 경우에만 시설 스펙이 이 클러스터에서 분리돼 증거 클러스터 자리(3번)로 올라간다 — 나머지 세 경우는 그대로 여기 유지.

### 블록 4-1. 분위기 (`atmosphere`)

**대조 체크**: STEP3 답변 있을 때만/없으면 null(유지) · about·philosophy와 독립, 감각적 디테일 위주(유지 — `about` 자체가 없고 `philosophy`도 "스튜디오 계기"로 범위를 좁혀둬서 겹칠 일이 더 적음) · 위치는 갤러리 인접(유지) · 2~3문장(유지).

**층1**: general과 동일, 변경 없음. `"atmosphere": { "text": "string" } | null`

**층2.5 (좋은/나쁜 예)**
좋은 예: "큰 창으로 오후 햇살이 들어오는 리포머룸, 은은한 로파이 음악, 1:1 수업이라 다른 회원 눈치 볼 일이 없는 조용함." — 감각적 디테일 + "눈치 안 봐도 됨"(초보자 불안과 자연스럽게 연결).
나쁜 예: "쾌적하고 좋은 시설을 자랑합니다" — 감각 디테일 없는 수식.

### 블록 4-2. 갤러리

**대조 체크**: 실제 사진만/4~8장 적정 → **개수 기준 하향**. 축B=갤러리우선이면 메뉴 앞 → 해당없음(축 자체를 안 씀, 위치는 클러스터로 고정).

**층2 (general 대비 변경)**
- **역할을 좁힌다**: `professionals`(인물)·`facility`(시설 스펙)·`transformations`(비포애프터) 중 어디에도 안 묶이는, **순수 분위기 전달용 사진만** 여기 배치한다. 트레이너 얼굴 사진은 `professionals.photo_url`로, 시설 스펙 증빙 사진은 `facility.photos`로 — 같은 사진을 갤러리에 중복 배치하지 않는다.
- **권장 개수 하향**: general의 4~8장은 "사진이 곧 설득력"인 업종(네일 등) 기준. 이 vertical은 특정 사실에 안 묶인 여유 사진(수업 현장샷, 단체컷 등)이 애초에 많지 않을 수 있어 1~4장도 충분. 없으면 그냥 `null`(완전 선택 블록).

**층2.5 (좋은/나쁜 예)**
좋은 예: 그룹 수업 진행 중 현장샷, 저녁 조명의 스튜디오 외관 — 특정 사실을 증명하지 않는 순수 분위기.
나쁜 예: 트레이너 얼굴이 크게 나온 프로필성 사진을 갤러리에도 중복 배치 — `professionals`와 겹침.

### 블록 4-3. 시설 스펙 (`facility`, 신규)

**층1 (슬롯 구조)**
```json
"facility": {
  "size_pyeong": "number | null",
  "has_shower": "boolean | null",
  "has_locker": "boolean | null",
  "has_parking": "boolean | null",
  "equipment_list": ["string"] | null,
  "photos": ["url"] | null
}
```
전체 항목이 다 비었으면 `facility: null`. 개별 항목은 모르면 각각 `null`(렌더러가 해당 항목만 숨김).

**층2 (작성 원칙)**
- **신뢰 스트립에 넣지 않기로 한 시설 지표(평수·운영시간 등)가 최종적으로 자리 잡는 블록**이다(블록 2 절 참고).
- `equipment_list`는 실제 보유 기구를 구체적 수량과 함께("리포머 5대", "캐딜락 2대") — general 메뉴 블록의 "재료·특징 구체적으로" 원칙과 같은 패턴.
- `photos`는 갤러리와 절대 안 겹치게 — 이 필드의 사진은 반드시 "이 스펙을 보여주는" 용도로만(기구 사진, 샤워실 사진 등).

**층2.5 (좋은/나쁜 예)**
좋은 예: `{ "size_pyeong": 45, "has_shower": true, "equipment_list": ["리포머 5대", "타워 2대"] }`
나쁜 예: `equipment_list: ["최신식 고급 장비들"]` — 구체성 없음, `copywriting.md`의 "구체성 없음=AI 티" 원칙 위반.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 4-1절 — 시설 스펙 아이콘 그리드는 이미 정의됨. 분위기·갤러리는 general 스타일 재사용, 팔레트만 이 vertical 톤 적용)

## 블록 5. 메뉴/서비스 (`menu`)

### 층1 (슬롯 구조)
general과 동일, 변경 없음 — `label` 필드가 이미 자유 텍스트라 "메뉴"라는 단어 자체를 안 쓸 수 있음.

### 층2 (작성 원칙)
- **`label`**: "메뉴"라는 단어를 쓰지 않는다. PT="PT 프로그램", 필라테스="수업 구성", 요가="클래스 안내" 등 세부 유형에 맞게 — `professionals.section_label`과 같은 패턴.
- **`mode`는 `item_consult`를 강하게 기본값으로.** `item_price`는 이 vertical에서 원칙적으로 쓰지 않는다(정찰제 그룹 클래스처럼 정말 고정가가 명확한 예외적 경우만). `package_table`은 코치 등급제처럼 구조가 명확할 때만 예외 허용 — 이때도 금액보다 등급 차이(경력·전문성) 설명에 무게를 둔다.
- **항목 수·설명 규칙은 general과 동일.**

### 층2.5 (좋은/나쁜 예)
**좋은 예:** `{ "label": "PT 프로그램", "mode": "item_consult", "items": [{ "name": "1:1 개인 PT", "price": null }] }` — "상담 문의"로 자연스럽게 렌더.
**나쁜 예:** `{ "label": "메뉴", "mode": "item_price", "items": [{ "name": "PT 10회", "price": "800,000원" }] }` — "메뉴"라는 단어도 안 어울리고, 고정가 노출이 `definition.md`의 강매 불안 원칙과 충돌.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 4-2절 — 강조색 없이 중립적으로, 가격 정보가 차분하게 보이도록)

## 블록 6. 위치/정보 (`info`)

### 층1 (슬롯 구조)
general과 동일, 변경 없음.

### 층2 (작성 원칙)
- **영업시간 뉘앙스**: 예약제 운영이면 "영업시간"을 "상담·수업 가능 시간대"로 이해하고 채운다 — 필드 구조는 그대로(`hours.structured`), 다만 이 시간대가 "워크인 가능 시간"이 아니라 "예약 가능 창구"라는 걸 염두에 두고 사장님이 준 시간 정보를 왜곡 없이 넣는다.
- **외부 링크 우선순위**: 이 vertical은 카카오톡 채널·인스타그램 DM이 실제 1차 상담 창구인 경우가 많다(상단고정바·CTA에서 이미 `guided` 모드로 정한 것과 같은 맥락) — 있으면 `external_links`에 반드시 포함해 상담 창구를 명확히 한다.
- **NAP·사업자정보는 general과 동일.**

### 층2.5 (좋은/나쁜 예)
**좋은 예:** `external_links: [{ "platform": "kakao", "url": "..." }]` — 실제 상담 창구를 명확히 노출.
**나쁜 예:** 시간 정보를 "24시간 언제든 방문 가능"처럼 예약제 사실과 다르게 표현 — `copywriting.md`의 사실 기반 원칙 위반.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` — 별도 신규 컴포넌트 없음, general 스타일 그대로 팔레트만 적용)

## 블록 7. 하단 고정 CTA바 (`sticky_cta`)

### 층1 (슬롯 구조)
general과 동일, 변경 없음 — `type` enum에 이미 `dm`이 포함돼 있어 구조 변경 불필요.

### 층2 (작성 원칙)
- **버튼 수·기본 구조는 general과 동일**(최대 2개, 메인+보조).
- **"작고 되돌릴 수 있게"라는 general 원칙이 이 vertical에서는 핵심 원칙으로 격상된다.** `definition.md`의 강매 불안이 방문자가 페이지를 떠나는 마지막 순간(스크롤 다 끝난 시점)에도 여전히 작동하기 때문 — 여기서마저 압박형 문구가 나오면 지금까지 쌓아온 신뢰가 마지막에 깨진다.
- **`cta_interaction_mode`는 상단고정바와 동일하게 `guided`를 기본값으로 강하게 유지.** 메인 버튼은 상담 창구(카카오·DM 등)로, 보조 버튼은 훨씬 더 낮은 부담의 선택지("인스타그램 둘러보기" 등 — 상담까지는 아직 부담스러운 방문자를 위한 탈출구).

### 층2.5 (좋은/나쁜 예)
**좋은 예:** 메인 `{ "type": "dm", "label": "카톡으로 편하게 물어보기" }` + 보조 `{ "type": "direction", "label": "인스타그램 둘러보기" }` — 부담 낮은 메인, 더 낮은 부담의 보조.
**나쁜 예:** `{ "type": "reservation", "label": "지금 등록하고 시작하기" }` — 페이지 끝까지 와서 마지막에 압박형 문구, 그동안 쌓은 신뢰가 무너짐.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` 4-2절 — 배경 `--brand-deep`, 버튼은 `accent-on-dark` 사용)

## 블록 8. 이용방법 (`how_it_works`)

### 층1 (슬롯 구조)
general과 동일, 변경 없음 — `steps: [{order, title, description}]` 구조가 이미 충분히 유연함.

### 층2 (작성 원칙)
- **general에선 선택 블록이지만, 이 vertical에서는 사실상 필수로 취급한다.** `definition.md`에서 이미 "상담→체험→등록 흐름을 명시해서 강매 불안을 구조적으로 해소하는 핵심 블록"이라고 못 박아뒀다.
- **표준 흐름을 구체적으로 지정한다**: 사장님이 체험 프로그램을 제공하면 **"상담 신청 → 체험 → 등록"(3단계)**, 체험이 없으면 **"상담 신청 → 등록"(2단계)**을 기본 골격으로 한다. 일반 원칙(2~4단계 자유)보다 좁힌 이유는, 이 흐름 자체가 "등록 전에 반드시 상담을 거친다"는 걸 방문자에게 구조적으로 보여줘서 강매 불안을 해소하는 장치이기 때문 — 사장님이 준 실제 절차와 다르게 지어내지 않되, 뼈대는 이 2안 중 하나로 정리한다.
- **"무인업종은 2단계로 압축" 원칙은 여기 적용하지 않는다.** 상담 단계를 생략한 "방문→등록"류의 2단계는 general 기준으론 짧고 효율적이지만, 이 vertical에서는 정확히 피해야 할 패턴이다 — 상담 단계가 빠지면 이 블록의 존재 이유 자체가 사라진다.
- **문구는 general과 동일**(손님 행동 중심 동사, 저부담 표현 — 상단바·CTA 원칙과 통일).

### 층2.5 (좋은/나쁜 예)
**좋은 예:** `[{ "title": "상담 신청" }, { "title": "체험 수업" }, { "title": "등록" }]` — 상담이 첫 단계로 명확히 존재.
**나쁜 예:** `[{ "title": "방문" }, { "title": "등록" }]` — 상담 단계가 빠진 2단계, 이 vertical에서는 강매 인상을 줄 위험.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` — general 스타일(숫자 스텝) 그대로, 팔레트만 적용)

## 블록 9. FAQ

### 층1 (슬롯 구조)
general과 동일, 변경 없음.

### 층2 (작성 원칙)
- **general 4개 원칙 전부 유지**(질문은 `industry-data.md` 예상 세트에서·중복 배제, 답변은 사실 그대로·지어내기 금지, 답변된 것만 포함, 구어체).
- **"초보자도 가능한가요?"는 이 vertical의 사실상 필수 후보 질문이다.** `definition.md` 5번 불안(나도 할 수 있을까)이 히어로 태그라인(첫 노출)·전문가 프로필(보강)에 이어 **여기서 명시적으로 마지막 확인**되는 자리 — 3곳 중 가장 직접적인 답을 주는 지점이다.
- **"상담받으면 무조건 등록해야 하나요?" 같은 강매 불안을 직접 이름 붙이는 질문도 강력한 후보다.** 단, `copywriting.md`의 지어내기 금지 원칙상 사장님이 실제로 확인해준 정책(예: "상담은 무료이며 등록 의무 없음")이 있을 때만 포함한다 — 없는 정책을 있는 것처럼 답하면 오히려 법적·신뢰 리스크.
- **업종 특유 후보 주제**(`industry-data.md`에 반영 예정): 환불 규정, 준비물(운동복·실내화 등), 락커·샤워시설 유무(단, 이 답은 `facility` 데이터와 일치해야 함 — 다른 블록과 모순 없이).

### 층2.5 (좋은/나쁜 예)
**좋은 예:** `{ "question": "운동 경험이 없는데 괜찮을까요?", "answer": "회원님의 70%가 운동을 처음 시작하신 분들이에요." }` — 사실 기반, 초보자 불안 직접 해소.
**나쁜 예:** `{ "question": "환불 가능한가요?", "answer": "네, 언제든 100% 환불해드립니다." }` — 사장님이 확인 안 해준 정책을 임의로 답하는 것, 절대 금지.

(디자인: `../../for-frontend/boutique-fitness/design-guide.md` — general 스타일(아코디언) 그대로, 팔레트만 적용)
